## 摘要
确保自动驾驶安全是一项关键挑战。基于场景的测试是验证自动驾驶系统（ADS）的系统性流程，但它仍然是一个碎片化的模块化流水线，其中场景生成、检索、修改、ADS执行和结果分析由彼此交互很少的独立工具完成。大语言模型（LLM）智能体已在感知、规划和控制等ADS子系统展现出潜力。然而，此前尚无工作以统一的LLM智能体框架覆盖ADS的整个基于场景的测试流水线。我们提出PlannerForge，一个LLM智能体框架，它扩展了所有基于场景的测试阶段（从场景生成到ADS评估），并新增两个LLM增强阶段：ADS增强和ADS基准测试。我们在5种提示条件下，使用10个现成LLM评估PlannerForge在所有任务（生成、选择、修改、模块路由、规划器测试和增强）上的表现。各任务最佳得分在0.88到1.00之间，开源20-35B后端在大多数任务上与商业API相当。Qwen3.6:35B等开源模型在五项任务中的三项上与商业API相当。端到端串联各模块可保留83%/78%的种子查询（商业/开源）。它在自然语言生成上优于Scenario Factory 2.0（Finkeldei et al., 2025）（200个中193个对144个可执行），并实现92-96%的所请求城市、道路和车辆属性。它在排名第1的选择上优于BM25（Robertson and Zaragoza, 2009）（92.0%对67.5%），并在物理有效编辑上优于From-Words-to-Collisions（Gao et al., 2025）（≥94%对31%）。在N=400时，成本调优将规划器成功率从50.4%提升至70.2%，并将碰撞从19.0%降至8.4%，且无需领域特定微调。

## Abstract
Ensuring the safety of autonomous driving is a critical challenge. Scenario-based testing is a systematic process used to validate Autonomous Driving Systems (ADSs), but it remains a fragmented modular pipeline in which scenario generation, retrieval, modification, ADS execution, and results analysis are performed by separate tools with little interaction. Large Language Model (LLM) agents have shown promise across ADS sub-systems such as perception, planning, and control. However, no prior work covers the whole scenario-based testing pipeline for ADSs with a unified LLM-agent framework. We present PlannerForge, an LLM-agent framework that extends all scenario-based testing stages (from Scenario Generation to ADS Assessment) and adds two further LLM-enhanced stages: ADS Enhancement and ADS Benchmarking. We evaluate PlannerForge with 10 off-the-shelf LLMs across all tasks (Generation, Selection, Modification, Module Routing, Planner Testing, and Enhancement) under 5 prompt conditions. Best-per-task scores range from 0.88 to 1.00, and open-source 20-35B backends match commercial APIs on most tasks. Open-source models such as Qwen3.6:35B match commercial APIs on three of the five tasks. Chaining the modules end-to-end retains 83% / 78% of seed queries (commercial / open). It outperforms Scenario Factory 2.0 (Finkeldei et al., 2025) on natural-language generation (193 vs. 144 executable of 200) and realises 92-96% of requested city, road and vehicle attributes. It outperforms BM25 (Robertson and Zaragoza, 2009) at rank 1 selection (92.0% vs. 67.5%) and From-Words-to-Collisions (Gao et al., 2025) on physically valid edits (>=94% vs. 31%). At N=400, cost-tuning lifts planner success from 50.4% to 70.2% and cuts collisions from 19.0% to 8.4%, without domain-specific fine-tuning.

## 2. 方法论

### 2.1 形式化框架
- 将 LLM 驱动的场景测试建模为一系列"自然语言 → 结构化输出"的决策：在对话轮 t，智能体观测 `x_t = (u_t, s_t, θ_t, h_t)`，分别对应用户话语、场景、规划器配置与对话历史。
- 会话由**生成** `f_gen: U → S` 或**选择** `f_sel: U × D → D` 初始化。
- **模块路由器**充当意图分类器：`â_t = argmax_{a∈A} f_router(a | u_t, h_t)`，动作集 `A = {MODIFY, TUNE, TEST, ANALYSE, QA}`。
- 各动作对应算子：`f_mod: S×U→S`、`f_tune: Θ×U→Θ`、`f_test: S×Θ→O`、`f_eval: O×U→Y`。
- 关键约束：`f_gen`、`f_mod`、`f_tune` 是**受限生成器**，其输出必须满足给定 schema（如 SUMO XML、CommonRoad XML、YAML），生成符合 schema 的结构化输出是核心语言学挑战。

### 2.2 系统架构与工程实现
- **技术栈**：Gradio 前端 + LangChain 后端；三层状态管理（LangChain 对话记忆、Gradio UI 历史、会话状态）。
- **场景数据库**：500+ 条 CommonRoad XML 场景，附带四层元数据（位置、路侧构造、参与者、自车），索引于 **Chroma 向量数据库**，使用 SentenceTransformer 嵌入。
- **仿真后端**：CommonRoad 场景格式 + SUMO 微观交通仿真 + CommonRoad–SUMO 接口；集成 **Frenetix**（采样式）与 **MP-RBFN**（学习式）两个规划器，统一在 `π_P(s, θ) = (τ, c, m)` 接口下。
- **地图来源**：OpenStreetMap 经 Overpass API（4 个镜像端点容错）获取，Nominatim/osmnx 做地名地理编码。

### 2.3 六大模块
- **Generation**：两阶段流水线。阶段一由 LLM 将自然语言解析为 JSON 意图（location / road classes / density / vehicle mix / duration），驱动 OSM 查询并转为 SUMO 仿真，再转 CommonRoad；阶段二由 LLM 选择自车（first car / by type / by index）并附加初始状态与目标区域。**LLM 只负责语言级任务，地图拓扑与车辆动力学由确定性工具生成，从结构上隔离三类幻觉**（非法 lanelet ID、运动学不可行轨迹、不存在的图元引用）。
- **Selection**：围绕四层元数据设计五步对话式槽位抽取（location → tags → road_net → obstacles → velocity），单调剪枝 `D^(k) = D^(k-1) ∩ match(ℓ̂_k)`，失败时回退到语义相似度检索。
- **Modification**：经 CommonRoad–SUMO 接口往返，支持四类编辑——轨迹重定向（T，两阶段：网络拓扑摘要 → 路由文件编辑）、行为预设（B，六种跟驰预设）、参与者增删（P）、目标区域（G，不经过 SUMO 往返）。
- **Module Router**：两阶段 LLM 函数调用——先识别模块并抽取参数返回 JSON，再由 Process Engine 分派。
- **Testing & Enhancement**：执行器 `f_test` 返回轨迹、碰撞标志与代价日志；调参器 `f_tune` 将定性预设或显式权重调整解释为 schema 合规的 YAML 覆盖，原地更新配置。
- **Analysis**：聚合批次统计、逐场景日志、当前配置与 CSV 路径四个上下文块，输出量化指标、失效模式分解（碰撞/超时/运动学不可行）及参数调整建议，与 `f_tune` 形成闭环。

### 2.4 提示技术
- 所有模块共享 curated-prompt（cp）头部，明确系统角色、输出 schema 与约束；在此之上叠加三种技术：**上下文提示（CP）** 注入结构化 schema 与可用算子、**思维链（CoT）** 结构化推理步骤、**上下文学习（ICL）** 少量正/负示例（含拒绝样例）。五种提示条件构成 baseline → cp → cp_cot → cp_icl → cp_icl_cot 的梯度。

## 5. 实验数量与充分性

- **实验规模**：每任务切片 200 条查询 × 10 个模型变体 × 5 种提示条件，共 8 个任务切片，结论部分称总计约 **80,000 次现成 LLM 调用**。Selection 模块需 10,000 次 LLM 抽取，产出 40,000 个（单元格，样本）检索结果；Modification 含 4 类编辑子任务；Generation 每个单元格聚合 200 次端到端运行（地理编码 → OSM 抓取 → CR 转换 → SUMO 仿真 → Frenetix 执行）。
- **消融维度**：提示条件梯度（5 档）即为主要的消融轴；此外 Selection 做了 4 种检索管线对比（funnel / semantic / hybrid_prefilter / RRF），Modification 做了 4 类编辑子任务的逐项消融，Enhancement 做了 5 种批量规模（N=50–400）× 3 轮独立调用的稳定性分析。
- **公平性考量**：
  - 优：对比基线时主动给 SF 2.0 其原生输入（目标城市）；BM25 与 LLM 共享同一检索后端；Enhancement 采用**逐场景配对评分**，且在固定（场景，配置）下规划器确定性，LLM 调用是唯一随机源。
  - 需注意：Router 的 `value %` 对复合动作的字母顺序敏感，作者额外报告 `set %` 与 `order %` 以解耦排序误差；Selection 的 sat_all 为严格 AND 契约，会放大单槽错误。
- **充分性评估**：整体实验覆盖面广、分层细致（附录给出逐单元格完整矩阵），并包含端到端链路验证与三个外部 SOTA 的横向对比。但存在两处客观缺口：**Analysis 模块未与 ground truth 对标评分**；**MP-RBFN 的对比仅为定性**（附录 A.7 明确说明定量对比属于进行中的扩展）；此外部分开源模型单元格在投稿时标注为 "N/A"（数据采集中）。

## 6. 主要结论与发现

- **模块级性能**：各任务最佳得分区间 **0.88–1.00**——Selection 0.880（最难）、Generation 0.957、Modification 四个子任务 headline 检查接近 100%、Router 0.997、Planner Testing 1.000。
- **开源模型可用性**：20–35B 开源后端在大多数任务上媲美商业 API；Qwen3.6:35b 在五项任务中的三项上与商业 API 持平，可完整驱动整条管线，无需领域微调。
- **端到端鲁棒性**：链路保留 **83%（商业）/ 78%（开源）** 的种子查询，均值成本约 126 s / 99 s 与 42.5k / 32.6k tokens 每场景；主要泄漏点为 Selection 与 Modification。
- **横向对比优势**：
  - Generation：193/200 可执行 vs. SF 2.0 的 144/200；实现 92–96% 所请求的城市/道路/车辆属性（SF 2.0 完全无法定向）；产生 7 类交通参与者（SF 2.0 为 4 类）；诱导 3.3 倍更多规划器碰撞（20.0% vs. 6.1%）。
  - Selection：rank-1 满足率 92.0% vs. BM25 67.5%（Any@5 差距较小，96.5% vs. 86.0%）。
  - Modification：物理有效率 ≥94% vs. FWtC 的 31%；参与者编辑（min_risk 1.84→1.20，58 个新碰撞）与目标编辑（1.84→1.36，45 个）对规划器的压力显著大于 FWtC 的有效编辑（1.84→1.69，16 个）。
  - Enhancement：N=400 时成功率 **50.4% → 70.2%**，碰撞 **19.0% → 8.4%**；所有批量规模均提升 17.6–21.3 pp，方差随 N 缩小（N=50 时 ±6.8 pp，N=400 时 ±0.3 pp）。
- **三条可迁移洞察**：
  1. **

1. **受限生成 + 确定性工具是抑制幻觉的结构性方案，而非后处理补丁**：PlannerForge 让 LLM 只承担"自然语言 → 中间表示（JSON/XML/YAML）"的语言级映射，地图拓扑、车辆运动学、图元引用等物理与拓扑合法性完全交给 Overpass/OSM、SUMO、CommonRoad 转换器等确定性工具生成。因此"非法 lanelet ID、运动学不可行轨迹、悬空图元引用"这三类典型幻觉**在结构上不可发生**，而不是靠事后校验剔除。这一范式可直接迁移到任何"LLM 生成安全关键工件"的领域（如测试用例、控制策略、形式化规约）。
  2. **提示工程收益呈"头部集中、尾部递减"**：curated-prompt（cp）头部（角色定义 + 输出 schema + 约束声明）贡献了主要增益，叠加 CoT 与 ICL 仅为增量改进。对工程落地的启示是：优先把 schema 契约与拒绝样例写清楚，再考虑推理链与示例注入，而非反向堆叠。
  3. **中等规模开源模型足以驱动全生命周期管线**：20–35B 的量化开源后端在五项任务中的三项上比肩商业 API，端到端种子保留率仅低约 5 pp（78% vs. 83%），却可在单张 32 GB 消费级显卡上本地运行，且无需任何领域微调。对数据敏感、需大规模重复实验的学术与工业验证场景，这显著降低了采用门槛。

## 7. 局限性与批判性审视

- **评测覆盖的空白**：
  - **Analysis 模块未设 ground truth**，仅作定性演示，无法回答"LLM 的失效模式归因与调参建议是否正确"这一关键问题，而这恰是与 `f_tune` 闭环的核心环节。
  - **MP-RBFN（学习式规划器）仅做定性对比**，附录 A.7 明确将其定量评测列为进行中的扩展；因此"跨规划器基准测试"这一新增阶段的普适性主张目前主要由 Frenetix 单一后端支撑。
  - 评测对象限于**运动规划器**，未触及感知、预测、行为决策等上游模块，结论向"完整 ADS 评估"外推时需谨慎。
- **统计严谨性**：除 Enhancement 的批量规模 × 3 轮重复外，多数任务未报告多次随机种子的置信区间或显著性检验，单元格间的细微差距（尤其接近 1.0 的 Router、Testing）可能落入运行间方差。
- **指标契约的放大效应**：Selection 采用严格 AND 的 `sat_all@returned`，单槽位错误即判负，会系统性压低绝对分数并可能低估语义近似正确的检索质量；Router 的 `value %` 对复合动作的字母序敏感，作者虽以 `set %`/`order %` 解耦，但主表口径仍需读者留意。
- **基线可比性的边界**：Generation 对比中 SF 2.0 被额外给定目标城市，属于"对基线更有利"的设置，方向上强化了本文结论，但也意味着两者并非在同一信息条件下比较；Modification 对比 FWtC 时，后者的物理有效率（31%）偏低可能与其原始设计目标（碰撞诱导而非 schema 合规）不完全对齐。
- **系统层面的开销**：端到端每场景约 126 s / 42.5k tokens（商业）与 99 s / 32.6k tokens（开源），在万级场景的回归测试中成本不可忽略；论文未讨论缓存复用、增量重跑或批处理调度等工程优化空间。

## 8. 对后续研究的启示

- **方法论层面**：PlannerForge 的价值不限于工具本身，而在于给出了"如何把 LLM 安全地接入安全关键工程流水线"的一套可复制模板——**对话式意图路由 + schema 受限生成 + 确定性工具实例化 + 定量评估闭环**。
- **可扩展方向**：将 Enhancement 从运动规划器权重扩展到感知/预测模块的配置空间；把 Analysis 接入带 GT 的失效标注以形成可度量的自优化回路；把 Benchmarking 阶段扩展到多规划器家族的标准化排行榜。
- **可复现性评价**：论文给出了精确的 provider model-id、Ollama 镜像标签、量化级别、上下文长度与硬件规格，开源模型在单卡消费级 GPU 上可完整复现，这一点明显优于多数依赖闭源 API 或大规模训练算力的同类工作。

## 9. 总体评价

PlannerForge 的贡献可以概括为"**一个框架 + 两个新阶段 + 一套证据**"：以统一的 LLM 智能体管线缝合了经典六阶段场景测试流程，新增 ADS 增强与跨规划器基准测试两个"LLM 时代"阶段，并用约 80,000 次调用、8 个任务切片、10 个模型 × 5 种提示条件的大规模矩阵验证了模块级性能（0.88–1.00）、开源模型可用性与端到端鲁棒性（83%/78%），并在 Generation、Selection、Modification 三个环节上以物理可执行性与规划器压力为标尺显著超越既有 SOTA。其主要短板在于 Analysis 环节缺乏定量评测、学习式规划器对比尚不完整，以及统计显著性报告的缺失。总体而言，这是一项工程完成度高、实验规模罕见、且具备清晰可迁移方法论的系统级工作。
